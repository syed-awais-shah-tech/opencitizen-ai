# OpenCitizen AI - Explicit Non-Goals (MVP Scope Boundaries)

**Document Version:** 1.0.0  
**Phase:** Stage 0 (MVP Product Specification)  
**Status:** Approved Specification  
**Related Documents:** [Product Requirements](product-requirements.md) | [User Flows](user-flows.md)

## Purpose

To ensure rapid, high-quality execution of the core MVP, this document explicitly defines what **OpenCitizen AI is NOT building during the initial MVP release**. Clear boundaries protect the project from scope creep, reduce unnecessary architectural complexity, and keep development laser-focused on evidence grounding, provenance, and verifiable data analysis.

---

## Explicit MVP Non-Goals

### 1. Optical Character Recognition (OCR) for Scanned or Handwritten Documents
* **Description:** OpenCitizen AI will not parse image-only scanned PDFs, photographed documents, or handwritten notes during MVP.
* **Scope Boundary:** Only digital text-layer PDFs (documents containing extractable digital text) are supported.
* **Rationale:** OCR adds heavy external dependencies (e.g., Tesseract, heavy vision models), significant processing latency, and character recognition errors that could compromise grounding accuracy.
* **Future Consideration:** Post-MVP ingestion plugin using an asynchronous OCR worker for historical municipal archives.

### 2. Multi-Tenant Enterprise Role-Based Access Control (RBAC)
* **Description:** Complex enterprise authorization models, hierarchical permissions, department-level access control lists (ACLs), and single sign-on (SAML/Okta) are out of scope.
* **Scope Boundary:** The MVP operates with simple workspace-level isolation suitable for individual researchers, local civic teams, and single-instance deployments.
* **Rationale:** Enterprise IAM adds substantial relational complexity that distracts from the core mission of verifiable retrieval and calculation inspection.
* **Future Consideration:** Milestone 5+ or dedicated enterprise deployment extension.

### 3. Live External Database Synchronization & Continuous ETL
* **Description:** OpenCitizen AI will not provide live, continuous synchronization connectors to external production data warehouses (e.g., Snowflake, BigQuery, Databricks) or operational transactional databases.
* **Scope Boundary:** Datasets must be provided as discrete, uploaded files (CSV or XLSX) or static exports.
* **Rationale:** Live data sync introduces schema drift, network resilience challenges, CDC (Change Data Capture) pipelines, and credential management burdens that are unnecessary for analyzing civic datasets.
* **Future Consideration:** Read-only S3/blob store integrations or direct URL dataset fetches.

### 4. Arbitrary Code Execution Sandbox (Python/R Interpreter)
* **Description:** The system will not execute arbitrary Python or R scripts generated by LLMs to calculate figures or generate plots.
* **Scope Boundary:** All numerical aggregations, sums, filters, and calculations are strictly executed as deterministic SQL queries within an in-process DuckDB engine. All chart rendering is performed client-side via Recharts.
* **Rationale:** Running arbitrary code in containers introduces severe security vulnerabilities (container escape, denial-of-service, unintended network calls) and obscures the calculation audit trail. DuckDB SQL is declarative, inspectable, and sandboxed by default.
* **Future Consideration:** None. Declarative SQL is an intentional architectural safeguard for auditability.

### 5. Multimodal Audio, Video, and Complex Diagram Analysis
* **Description:** Ingesting audio from city council hearings, video recordings of public meetings, or complex vector CAD drawings is out of scope.
* **Scope Boundary:** Input modalities are strictly limited to text documents (PDF) and tabular data (CSV/XLSX).
* **Rationale:** Media transcription and computer vision pipelines introduce high compute costs, complex storage requirements, and non-trivial error rates.
* **Future Consideration:** Automated transcription ingestion pipeline for meeting audio in subsequent milestones.

### 6. Autonomous Web Scraping & Open Internet Browsing
* **Description:** The system will not deploy autonomous web browsing agents or search engine crawlers to fetch live web pages during query processing.
* **Scope Boundary:** Answers are strictly grounded in user-uploaded documents and datasets. If the answer is not in the uploaded files, the system declines to answer.
* **Rationale:** Allowing live web search reintroduces hallucinations, source unreliability, and unpredictable latency. OpenCitizen AI's primary value proposition is inspectable provenance over explicitly provided records.
* **Future Consideration:** Controlled, user-configured ingestion of specific public portal URLs before querying.

### 7. Direct Database Write-Backs & Data Mutation
* **Description:** Users cannot modify, insert, delete, or clean original dataset records via the chat interface or natural language commands.
* **Scope Boundary:** All analytical queries against DuckDB and metadata storage are strictly read-only (`SELECT` queries only).
* **Rationale:** Civic auditability requires absolute data immutability. An analyst or citizen must know that the underlying dataset has not been altered during questioning.
* **Future Consideration:** Read-only virtual views or derived dataset exports without mutating source data.

### 8. Custom Model Training, LoRA Fine-Tuning, & Local GPU Weight Serving
* **Description:** The MVP will not host self-hosted model weights (e.g., vLLM, Ollama) or perform fine-tuning of model parameters.
* **Scope Boundary:** The MVP interfaces with the Gemini API through a strictly typed `AIProvider` abstraction layer, complemented by a mock provider for deterministic offline testing.
* **Rationale:** Self-hosting multi-billion parameter LLMs demands expensive local GPU infrastructure, complicates local developer setup, and slows rapid iteration. The provider abstraction ensures alternative backends can be plugged in later without rewriting business logic.
* **Future Consideration:** Optional local Ollama/vLLM provider adapter in Milestone 5.

### 9. Real-Time Collaborative Multi-User Editing (Multiplayer Canvas)
* **Description:** Real-time multi-cursor collaboration (e.g., Google Docs or Figma-style simultaneous collaborative query crafting) is not supported.
* **Scope Boundary:** Users interact with their workspaces independently. Workspaces and query audit reports can be shared via export (JSON/PDF).
* **Rationale:** Concurrent real-time collaboration adds operational complexity (OT/CRDT algorithms, state sync) that is secondary to analytical accuracy.
* **Future Consideration:** Workspace sharing with read-only view links.

### 10. Automated Scheduled Crawls & Webhook Receivers
* **Description:** OpenCitizen AI will not run background cron daemons or webhook endpoints to automatically pull updates from government transparency portals.
* **Scope Boundary:** All document and dataset ingestion is initiated manually by users through the UI or REST API.
* **Rationale:** Autonomous schedulers require complex state management, failure retry logic, and monitoring infrastructure that would delay the core MVP delivery.
* **Future Consideration:** Extensible webhook ingestion service post-v1.0.

## Summary of MVP Boundaries

| Capability | In Scope for MVP | Explicit Non-Goal (Post-MVP) |
| :--- | :--- | :--- |
| **Document Formats** | Digital text PDFs | Scanned image PDFs, OCR, handwritten notes |
| **Dataset Formats** | CSV, XLSX files | Live database CDC, BigQuery/Snowflake connectors |
| **Analytics Engine** | Read-only DuckDB SQL | Arbitrary Python/R sandbox execution |
| **Visualization** | Dynamic Recharts components | Custom BI report builder / dashboard layout designer |
| **Auditability** | Exact page citations & SQL query trace | Real-time multi-user auditing and sign-offs |
| **AI Provider** | Gemini API via `AIProvider` & Mock | Self-hosted local LLM GPU clusters, fine-tuning |
| **Collaboration** | Workspace sessions & report exports | Real-time concurrent multi-cursor editing |
